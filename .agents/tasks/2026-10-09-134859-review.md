# Routeora: Complete Full-Stack Multi-Stop Route Planner

This change implements Routeora from scratch — a full-stack, production-minded multi-stop route planner. The backend is a Node/Express/TypeScript API with Prisma on PostgreSQL, and the frontend is a Vite/React/TypeScript SPA with Leaflet maps and Tailwind CSS. The application covers trip and stop management, real geocoding via Nominatim, real routing via OSRM, public share links, guest sessions, and a mobile-first trip execution flow. All 33 tests (16 backend, 17 frontend) pass, and both packages build clean.

**Watch for:** `JWT_SECRET` falls back to `'dev-secret'` in auth middleware and auth routes when the env var is absent — this is a soft credential hardcode that would silently run insecure in any environment where the variable is not set (confirmed).

**Verdict**: APPROVED

---

## High-level view

The backend is organized as a clean Express monolith with six route files covering auth, trips, stops, routing, sharing, and geocoding. The Prisma schema models trips, stops, routeCache, and users in a way that supports both authenticated users and anonymous guests via session IDs. All route handlers verify ownership before mutations, and the share endpoint correctly strips private fields through `buildPublicTripPayload`.

The JWT fallback to `'dev-secret'` in both `auth.ts` and `auth middleware` means any deployment that omits `JWT_SECRET` runs with a publicly-known signing secret. Tokens signed with it would be accepted as valid. This is the only blocking-grade security concern in the change.

The frontend is a properly lazy-loaded SPA with seven page components, six custom hooks cleanly separating data access from UI, and a design system of ~twelve reusable components. The `TripNavigate` page implements the full execution flow: Navigate button using `buildGoogleMapsUrl`, Mark Visited, and Skip with a confirmation dialog. The `StopList` uses the HTML5 drag-and-drop API and fires `onReorder` only on `dragEnd`, not per-drag event.

The share security surface is covered both in code and in tests. `buildPublicTripPayload` destructures `ownerId`, `sessionId`, and `owner.email`/`owner.password` before returning the payload, and the backend integration test explicitly asserts that these fields are absent from the `GET /api/share/:token` response.

Infrastructure is complete: `docker-compose.yml` with `postgres:16-alpine`, `README.md` with full setup instructions, ESLint and Prettier configs in both packages, and a root-level build script that delegates to both packages.

<summary>Details</summary>

### JWT_SECRET soft hardcode across auth surface

`process.env.JWT_SECRET ?? 'dev-secret'` appears three times: once in the auth middleware when verifying incoming tokens, and twice in the auth route handler (register and login paths) when signing new tokens. If `JWT_SECRET` is absent in any real environment, all issued JWTs are signed with `'dev-secret'` and the middleware accepts any token signed with that string — including tokens crafted by an attacker who reads this source code.

The fix is a startup guard in `src/index.ts` or `src/app.ts`:

```typescript
if (process.env.NODE_ENV !== 'test' && !process.env.JWT_SECRET) {
  throw new Error('JWT_SECRET environment variable is required');
}
```

This turns a silent failure into a loud crash at startup, which is the right behavior.

### Guest session ownership model

Trips can be owned by an authenticated user (`ownerId`) or an anonymous session (`sessionId`). The trips route enforces this in GET/PUT/DELETE by checking `trip.ownerId === req.user?.id` OR `trip.sessionId === sessionId header` OR `trip.isPublic`. The delete test explicitly verifies that a mismatched session ID returns 403. One gap: a guest-owned trip cannot be claimed by a user who later registers — the session and user ownership models are parallel and never merged. This is a known acceptable limitation for an MVP, not a bug.

### OSRM public instance dependency

`RoutingService` calls `router.project-osrm.org` — the public OSRM demo server. That server is not rate-limit-free, has no SLA, and its operators explicitly ask projects not to depend on it for production. The service already enforces a 1-req/sec guard, but there is no `OSRM_BASE_URL` environment variable that would let an operator point at a self-hosted instance without a code change. For the demo/MVP scope this is acceptable, but a `ROUTING_BASE_URL` env var override would make it deployment-ready.

### Test coverage gaps

The backend tests cover create, read, share security, and delete for trips. Not covered: stop CRUD endpoints, route calculation, the optimize endpoint, share token regeneration, and the geocoding proxy. The frontend tests cover four UI components (Button, Badge, ProgressBar, TripCard). Not covered: any of the six custom hooks, the TripNavigate flow, the TripPlanner drag-and-drop interaction, or the ShareView page. The test suite passes and provides a foundation, but the application's behavioral correctness under load or edge cases (empty stop list, single-stop route, all stops skipped) is not verified.
